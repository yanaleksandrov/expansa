Класс **Asset** предназначен для подключения JS и CSS файлов.
Рекомендуется использовать именно его для этих целей, так как
имеет преимущества перед подключением напрямую через теги
`<link rel="">` или `<script src=""></script>`.

Плюс в том, что вы получаете гибкость в управлении этими ресурсами:
можно переопределять последовательность подключения, избавиться от конфликтов
связанных с зависимостями, контролировать отсутствие дублей подключений,
а также подключать новые виды ресурсов (шрифты, preload и т.д.), не трогая ядро.
И всё это из любой точки приложения.

> Важная ремарка. Во frontend части Expansa CMS отсутствует подключение ресурсов
"по умолчанию". Будь то jQuery (привет WordPress), React, Vue или другой фреймворк.
Такой подход позволяет иметь полную свободу над содержимым вебсайта. С другой стороны,
Expansa CMS поставляется вместе с упомянутыми и другими популярными библиотеками.
О том, как их подключить смотрите ниже.

## Состояния ресурсов

У каждого ресурса есть два состояния: добавленный в очередь (enqueued) и используемый (used).

Добавленный в очередь — это состояние, при котором ресурс только загружен в хранилище **Asset**.
Это означает, что **Asset** знает о существовании этих ресурсов, но не будет подключать их к документу во время рендеринга.

Используемый — это состояние, при котором **Asset** подключит эти ресурсы и их зависимости к документу во время рендеринга.

Ресурс не может быть использован, если ранее он не был зарегистрирован.

## Добавление ресурса в очередь

Самый низкоуровневый способ — метод `enqueue`. Он принимает провайдера (тип ресурса) третьим
параметром:

```php
Asset::enqueue($uid, $src, $provider, ...$data);
```

**$uid** *(строка) (обязательный)*: Строка в стиле "kebab-case" в нижнем регистре. Уникальный для ресурса идентификатор.

**$src** *(строка) (обязательный)*: URL файла, либо путь относительно корня Expansa. Например: `http://example.com/themes/my-theme/my-theme-script.js`.

Не нужно писать URL жёстко, он должен определяться динамически, например через функцию `url()`.

**$provider** *(строка) (обязательный)*: ключ зарегистрированного провайдера — `css` или `js` из коробки
(см. [Регистрация собственных провайдеров](#регистрация-собственных-провайдеров)).

**...$data** *(массив)*: дополнительные атрибуты тега (`class`, `media`, `async`, `defer`, `dependencies`, ...) —
их полный список смотрите в конструкторах `Expansa\Assets\Providers\Link` и `Expansa\Assets\Providers\Script`.

На практике вместо `enqueue()` почти всегда используются два коротких метода:

```php
Asset::style('main', '/themes/my-theme/main.css');
Asset::script('main', '/themes/my-theme/main.js', ['async' => true]);
```

## Примеры подключения

### #1 Подключение с дополнительными атрибутами

```php
Asset::script('main', 'path/to-file/main.js', ['defer' => true, 'crossorigin' => 'anonymous']);
```

### #2 Загружаем скрипт с нестандартного адреса через CDN

Допустим, вы хотите вместо библиотеки jQuery из состава Expansa подключить её CDN-копию.
`override()` сам определит провайдера — сперва по расширению нового `$src` (если оно совпадает с
зарегистрированным провайдером), и только если это не удалось — по тому, чем `uid` обслуживался
раньше. Указывать провайдер вручную не нужно:

```php
Asset::override('jquery', '//ajax.googleapis.com/ajax/libs/jquery/1.7.2/jquery.min.js');
```

Если у `uid` одновременно зарегистрированы и стили, и скрипт (обычный случай для `style()` +
`script()` под одним именем), `override()` заменяет только тот из них, что совпадает с провайдером
нового ресурса — второй не трогается.

### #3 Регистрируем штатный скрипт "alpine.js"

```php
Asset::script('alpine', '/expansa/assets/js/vendor/alpine.min.js');
```

### #4 Автоматическое подключение CSS/JS «по файлам»

Часто CSS и JS нужны только тогда, когда конкретный файл шаблона реально участвует в рендере
страницы — и должны лежать рядом с ним, а не регистрироваться вручную в коде на все случаи жизни.

Для этого у `Asset` есть метод `discover()`. Он ничего не знает о View, Blade или любом другом
компоненте фреймворка — это просто "если рядом с файлом `$file` лежит `$file.css` / `$file.js`,
подключи их". Метод работает с любым файлом, из любого места приложения, и ничего не подключает
автоматически сам по себе — вызвать его нужно явно там, где вам это нужно:

```php
Asset::discover('/absolute/path/to/index.blade.php');
// найдёт и подключит index.css и index.js рядом с ним, если они существуют
```

Ядро Expansa (`Expansa\View`, `Expansa\Assets`) намеренно ничего не знает друг о друге — ни один
компонент фреймворка не вызывает `discover()` сам. Связка делается на уровне приложения, в
`app/Controllers/Web.php`, ровно там, где уже рендерится страница:

```php
$content = view($page ?? 'index', [...]);

// index.css / index.js рядом с index.blade.php подключатся сами, если существуют
Asset::discover($content->getPath());

$content = $content->beautify()->render();
```

Поэтому на практике достаточно положить `index.css`/`index.js` рядом с `index.blade.php` темы —
они подключатся автоматически при рендере страницы, без единой строчки
`Asset::style()`/`Asset::script()`:

```
views/
├── index.blade.php
├── index.css   ← подключится автоматически
└── index.js    ← подключится автоматически
```

Важно: это подключение работает на уровне **шаблона страницы, который явно рендерит app**, а не
автоматически для каждого вложенного partial/компонента (Expansa не перехватывает рендер каждого
`@include`, чтобы не привязывать `View` к `Assets`). Если нужно то же самое для конкретного
компонента/partial-а, вызовите `discover()` явно в его собственном коде — например, в начале файла
компонента, если он рендерится через обычный PHP:

```php
Asset::discover(__FILE__); // подключит card.css/card.js рядом с card.php
```

Если нужно сгруппировать несколько файлов под одним общим `uid` (например, чтобы вместе
включать/выключать их через `render(['uid' => '...'])`), передайте второй аргумент:

```php
Asset::discover($path, 'page');
```

Повторные вызовы `discover()` для одного и того же файла безопасны: ресурсы дедуплицируются по
`id`, так что нет риска подключить один и тот же файл дважды.

#### Метод configure(): где лежат CSS/JS и как называются

По умолчанию `discover()` ищет CSS/JS рядом с файлом, под тем же именем (`card.blade.php` →
`card.css` + `card.js`). Это только конвенция по умолчанию, а не жёсткое правило — она полностью
заменяется методом `Asset::configure()`. Резолвер получает абсолютный путь до файла и возвращает
карту `ключ провайдера => путь до файла`; что вернуть — решаете вы, поэтому имена CSS/JS не
обязаны совпадать с именем PHP-шаблона и даже лежать с ним рядом:

```php
// Стили и скрипты лежат в общих папках assets/css и assets/js,
// а не рядом с шаблоном, и называются по папке компонента, а не по имени PHP-файла.
Asset::configure(resolver: function (string $file): array {
    $name = basename(dirname($file)); // views/card/card.blade.php -> "card"

    return [
        'css' => EX_PATH . "assets/css/$name.css",
        'js'  => EX_PATH . "assets/js/$name.js",
    ];
});
```

```php
// Фиксированные имена style.css/script.js рядом с шаблоном, независимо от того,
// как называется сам файл шаблона (card.blade.php, index.php, ...).
Asset::configure(resolver: fn (string $file): array => [
    'css' => dirname($file) . '/style.css',
    'js'  => dirname($file) . '/script.js',
]);
```

Резолвер настраивается один раз (например, в `configs.php` темы или плагина) и действует для всех
последующих вызовов `discover()`. Ключи возвращаемого массива — это ключи провайдеров
(`'css'`, `'js'`, или любой ваш, зарегистрированный через `Asset::provider()`); путь, для которого
`is_file()` не находит файл, просто пропускается, так что резолвер не обязан проверять
существование сам.

Результат `discover()` кэшируется в памяти на время запроса по паре (файл, `$context`) — повторный
вызов для той же комбинации не обращается к диску снова, а отдаёт уже посчитанный результат (это
особенно заметно там, где на одной странице повторяется много однотипных полей формы). Именно
поэтому важно настраивать `configure()` один раз в начале запроса, а не переключать резолвер
посреди рендера — кэш держит результат резолвера, а не сам резолвер, и не узнает, что тот
поменялся.

Важно: резолвер, переданный в `configure()`, заменяет конвенцию по умолчанию для **всех** вызовов
`discover()` в приложении, а не только для тех файлов, ради которых вы его писали. Если он должен
обрабатывать лишь часть файлов, для остальных явно верните встроенную конвенцию через
`Manager::defaultStructure($file)`, а не пустой массив — иначе автоподключение молча перестанет
работать везде, где вы не думали, что оно вообще есть.

#### Пример из дашборда: vendor JS только для тех полей формы, что реально используются

В дашборде часть JS-виджетов (`youla-select.js` и т.п.) раньше подключалась безусловно на каждой
странице — независимо от того, есть ли на ней вообще поле нужного типа. С `discover()` и
`configure()` это подключение стало условным: скрипт грузится только на страницах, где
`Field::parse()` реально рендерит соответствующее поле.

Отдельная сложность в том, что несколько разных по смыслу типов полей (`date`, `range`, `color`,
обычный текст) используют **один и тот же** файл шаблона — `form/input.blade.php` (см.
`Field::parse()`: они все схлопываются в тип `input` перед рендером). По одному только имени файла
их не различить, поэтому `discover()` умеет принимать третий аргумент `$context` — то, что не
следует из пути к файлу, но известно в момент рендера — и передавать его вторым аргументом в
резолвер `configure()`.

В `Expansa\Builders\Forms\Field::parse()`, там же, где рендерится шаблон поля, до схлопывания типа
запоминается исходный подтип поля:

```php
// $type ещё не схлопнут в 'input' — сохраняем его для discover().
$inputType = $type;

if (in_array($type, ['color', 'date', /* ... */], true)) {
    $type = 'input';
}

// ...

$view = View::make("form/{$prefix}{$type}", $field);

// $inputType используется и как uid, и как контекст: без этого color-поле и date-поле
// на одной странице столкнулись бы на одном uid "input" от общего шаблона, и второе
// поле по рендеру молча осталось бы без своего скрипта (enqueue дедуплицирует по id).
Asset::discover($view->getPath(), $inputType, ['type' => $inputType]);

$content .= $view;
```

А в `dashboard/index.php` резолвер использует и путь к файлу, и этот контекст:

```php
use Expansa\Assets\Manager;

$suffix = ! Is::debug() ? '.min' : '';

Manager::configure(resolver: function (string $file, array $context = []) use ($suffix): array {
    if (! str_contains(str_replace('\\', '/', $file), '/dashboard/views/form/')) {
        return Manager::defaultStructure($file); // всё остальное — по конвенции по умолчанию
    }

    $template      = basename($file, '.blade.php');
    $inputType     = $context['type'] ?? '';
    $dateTimeTypes = ['date', 'datetime-local', 'time', 'month', 'week'];

    $vendor = match (true) {
        $template === 'select'                     => 'youla-select',
        $template !== 'input'                      => null, // form/input.blade.php — единственный, у кого есть подтипы
        $inputType === 'color'                     => 'youla-filler',
        in_array($inputType, $dateTimeTypes, true) => 'youla-pickadate',
        $inputType === 'range'                     => 'youla-ranger',
        default                                    => null,
    };

    return $vendor === null
        ? Manager::defaultStructure($file)
        : ['js' => EX_PATH . "dashboard/assets/js/$vendor$suffix.js"];
});
```

Скрипты, нужные почти всем полям сразу (`youla-tooltip.js` — подсказки есть и у `select`, и у
`input`, и у `timezone`), а также сам движок дашборда (`youla`, `youla-ajax`, `youla-expansa`)
по-прежнему стоит подключать безусловно, как раньше — автоподключение по файлу имеет смысл только
там, где ресурс действительно нужен не всем, а конкретному, отличимому подмножеству страниц.

### #5 Удаление версии скрипта или файла стилей из URL

При регистрации скрипта ему можно указать версию, например: `/assets/js/alpine.js?ver=2025.1`.
Это делается через параметр `version` в `...$data`:

```php
Asset::script('alpine', '/assets/js/alpine.js', ['version' => EX_VERSION]);
```

### #6 Добавление инлайн-данных

Массив, переданный в `$data`, попадает в свойство `data` ресурса. Если он не пуст, `Script`
перед тегом `<script>` выводит `<script>var alpine = {...}</script>` с этими данными,
доступными на клиенте под именем, производным от `uid`:

```php
Asset::script('alpine', '/assets/js/alpine.min.js', ['data' => ['debug' => true]]);
```

## Регистрация собственных провайдеров

Из коробки `Asset` умеет подключать CSS (`Expansa\Assets\Providers\Link`) и JS
(`Expansa\Assets\Providers\Script`). Список провайдеров — это открытый реестр
"ключ → класс" (`Asset::provider()`), а не жёстко зашитый `switch` внутри `Manager`, поэтому плагины
и темы могут добавлять свои виды ресурсов (шрифты, `<link rel="preload">`, importmap-ы и т.д.), не
трогая ядро. Ниже — пошагово, на примере подключения шрифтов.

### Шаг 1. Что обязан уметь провайдер

Любой провайдер — это класс, унаследованный от `Expansa\Assets\Abstracts\Provider`. Абстрактный
класс требует реализовать два метода:

- `render(Provider $asset, bool $minify = false, bool $inline = false): string` — вернуть HTML-тег
  для одного ресурса; `$minify`/`$inline` приходят из вызова `Asset::render()`, а не хранятся на
  самом ресурсе (см. [Минификация и встраивание](#минификация-и-встраивание)).
- `minify(string $code): string` — минифицировать содержимое ресурса (если для вашего типа
  минификация не имеет смысла, как для шрифтов, просто верните `$code` без изменений).

Необязательно, но при желании можно переопределить и `renderInline(Provider $asset, string $content): string`
— как обернуть уже готовое содержимое (например, при `combine: true, inline: true`) в тег без
`href`/`src`. По умолчанию просто откатывается на обычный `render()`; переопределять есть смысл
только если «встроенное содержимое» вообще имеет смысл для вашего типа ресурса (для шрифта,
например, нет).

Ещё один необязательный метод — `preamble(Provider $asset): string`. По умолчанию возвращает
пустую строку; переопределите его, если вашему ресурсу нужна разметка рядом с тегом, которая не
должна ни минифицироваться вместе с содержимым, ни оказаться внутри закэшированного/объединённого
файла (пример — `data`-дамп у `Script`, см. [Объединение файлов](#объединение-файлов)).
`Manager::render()` вызывает `preamble()` и для одиночных ресурсов, и — отдельно на каждый
входящий кусок — при `combine: true`.

Кроме этого, `Manager` при рендере и сортировке очереди обращается к нескольким свойствам объекта
напрямую (через `AssetHandler::sortDependencies()` и фильтр в `render()`), поэтому провайдер
должен их объявить:

| Свойство        | Тип      | Зачем нужно |
|-----------------|----------|-------------|
| `uid`           | `string` | идентификатор ресурса, по нему работают `get()`, `dequeue()`, `override()` |
| `id`            | `string` | ключ хранения в `Manager::$assets`, должен быть уникален (обычно `"{$uid}-{extension}"`) |
| `dependencies`  | `array`  | uid’ы (или id’ы) ресурсов, которые должны выводиться раньше |
| `toFooter`      | `bool`   | попадёт ли ресурс в `render(['toFooter' => true])` (подвал) или в `false` (`<head>`) |

Проще всего объявить их как параметры конструктора (как это делают `Link` и `Script`), а `id` —
как вычисляемое свойство через property hook (PHP 8.4), чтобы не дублировать логику вручную.

### Шаг 2. Пишем провайдер

```php
namespace App\Assets;

use Expansa\Assets\Abstracts\Provider;

class Font extends Provider
{
    public function __construct(
        public string $uid,
        public string $src,           // путь/URL до файла шрифта, например .woff2
        public array $data = [],
        public string $type = 'font/woff2',
        public string $crossorigin = 'anonymous',
        public array $dependencies = [],
        public bool $toFooter = false, // шрифты обычно preload-ятся в <head>
        public string $path = '',
    ) {
        $this->path = self::toPath($src);
    }

    /**
     * Ключ хранения в очереди — вычисляется, а не хранится отдельным полем.
     */
    public string $id {
        get => sprintf('%s-font', $this->uid);
    }

    public function render(Provider $asset, bool $minify = false, bool $inline = false): string
    {
        // Шрифт минифицировать/инлайнить нечем, оба параметра для этого провайдера смысла не имеют.
        $attributes = $this->sanitizeAttributes([
            'rel'         => 'preload',
            'as'          => 'font',
            'href'        => $asset->src,
            'type'        => $asset->type,
            'crossorigin' => $asset->crossorigin,
        ]);

        return sprintf("\t<link%s>\n", $attributes);
    }

    public function minify(string $code): string
    {
        // Бинарный файл шрифта минифицировать нечем — возвращаем как есть.
        return $code;
    }
}
```

`sanitizeAttributes()` доступен «из коробки» — он приходит вместе с `Provider` через трейт
`AssetHandler` и берёт на себя экранирование и сборку строки атрибутов, как это делают `Link` и
`Script`.

### Шаг 3. Регистрируем провайдера

Обычно это делается один раз при старте приложения/плагина (например, в `configs.php` или в
`index.php` плагина/темы):

```php
use Expansa\Facades\Asset;
use App\Assets\Font;

Asset::provider('font', Font::class);
```

Если передать класс, не унаследованный от `Provider`, `Asset::provider()` выбросит
`InvalidArgumentException` — опечатку в конфигурации сразу будет видно.

### Шаг 4. Подключаем ресурс и выводим его

Готового шортката вроде `Asset::style()`/`Asset::script()` для новых провайдеров нет — они
подключаются через низкоуровневый `enqueue()`, указав ключ провайдера третьим параметром:

```php
Asset::enqueue('brand-heading', '/themes/my-theme/fonts/heading.woff2', 'font');
```

Дальше ресурс ведёт себя как любой другой: попадает в общую очередь, участвует в сортировке по
`dependencies` и выводится через `render()` вместе с CSS/JS:

```php
Asset::render(['toFooter' => false]);
// ...
// <link rel="preload" as="font" href="/themes/my-theme/fonts/heading.woff2" type="font/woff2" crossorigin="anonymous">
```

Если в теме используется несколько шрифтов, для удобства можно завести собственный хелпер поверх
`enqueue()` (например, `App\Support\font($uid, $src)`) — это уже вопрос вкуса конкретного проекта,
а не требование `Asset`.

## Управление очередью

```php
Asset::get('alpine');              // все ресурсы с данным uid (может быть css и js одновременно)
Asset::get();                       // все зарегистрированные ресурсы
Asset::dequeue('alpine');           // убрать все ресурсы с данным uid
Asset::dequeue('alpine', 'css');    // убрать только css-часть, оставив js-часть (если есть)
```

## Порядок и зависимости

Ресурсы выводятся в порядке добавления, но с учётом зависимостей: если у ресурса указан
`dependencies`, он гарантированно выводится после того, от чего зависит. В `dependencies`
можно указывать как `uid` зависимости, так и её полный `id`:

```php
Asset::script('vendor', '/assets/js/vendor.js');
Asset::script('main', '/assets/js/main.js', ['dependencies' => ['vendor']]);
```

## Использование ресурса

Вывод очереди в HTML выполняется методом `render()`. Обычно он вызывается дважды за страницу: один
раз в `<head>`, второй — перед закрывающим `</body>`, а какие ресурсы куда попадают, решает
свойство `toFooter` (по умолчанию `true` для скриптов и `false` для стилей):

```php
Asset::render(['toFooter' => false]); // всё, что должно быть в <head>
Asset::render(['toFooter' => true]);  // всё, что должно быть перед </body>
```

Первый аргумент — произвольный фильтр: ассоциативный массив, где ключ — это имя свойства ресурса
(`uid`, `path`, `toFooter`, ...), а значение — либо точное значение, либо маска с `*`:

```php
Asset::render(['uid' => 'notifications']);
Asset::render(['path' => '*.js']);
```

Кроме фильтра, `render()` принимает ещё три именованных параметра — `combine`, `minify` и
`inline`. Все три относятся не к конкретному ресурсу, а к тому, **как именно** рендерить весь
набор, отобранный фильтром, поэтому это параметры вызова `render()`, а не что-то, что указывается
при регистрации ресурса через `enqueue()`/`style()`/`script()`.

```php
Asset::render(['toFooter' => false], combine: true, minify: true);
```

### Минификация и встраивание

`minify` и `inline` — два независимых булевых флага (по умолчанию оба `false`, то есть ничего не
меняется — файл отдаётся браузеру как есть):

```php
Asset::render(['toFooter' => false], minify: true);              // минифицировать в отдельный файл
Asset::render(['toFooter' => false], inline: true);               // встроить как есть, без минификации
Asset::render(['toFooter' => false], minify: true, inline: true); // минифицировать и встроить
```

**`minify`** — запускает `minify()` провайдера над содержимым файла перед выводом.

**`inline`** — встраивает содержимое (минифицированное или как есть — зависит от `minify`) прямо
в разметку: `<style>...</style>` вместо `<link>`, `<script>...</script>` вместо `<script src="">`.
Экономит HTTP-запрос, но теряет кэширование браузером — имеет смысл только для действительно
маленьких файлов. Ничего не даёт для внешнего ресурса (URL, не указывающего на локальный файл) —
инлайнить нечего, такой ресурс всегда рендерится как обычно.

`Link` (`style()`) также используется для `<link>`-тегов, которые вовсе не CSS — favicon
(`rel="icon"`), `apple-touch-icon`, `manifest` и т.п. (см. пример #1 в начале документа). Для них
`minify`/`inline` тоже ничего не делают — срабатывают только при `rel === 'stylesheet'` (значение
по умолчанию у `Link`), иначе PNG/ICO/webmanifest попытался бы минифицироваться как CSS-текст и
испортился бы. `combine` их тоже не трогает — по той же причине, что и любой другой ресурс с
нестандартным `rel`, он не проходит проверку «ничего не потеряется при объединении».

Без `inline` (то есть `minify: true, inline: false`) минифицированное содержимое сохраняется в
`cache/assets/{css|js}/` под именем `{uid}-{хэш содержимого}.{расширение}` (директория создаётся
автоматически при первом использовании), а тег рендерится как обычно (`<link>`/`<script src="">`),
но ссылается на этот файл. Раз имя файла зависит от хеша содержимого, смена содержимого сама по
себе даёт новый URL — отдельная версия (`?ver=`) для сброса кэша браузера не нужна, и обновляется
это сразу же, без очистки какого-либо кэша: хэш каждый раз считается заново от содержимого файла
на диске, а не запоминается между запросами. Если содержимое не поменялось — хэш тот же, файл
просто переиспользуется, ничего заново не пишется; старые файлы под прежними хэшами при этом никуда
не деваются — они больше ни на что не ссылаются, но физически остаются в `cache/assets` (см. ниже,
как их подчищать).

Если записать файл в `cache/assets` не получилось (диск заполнен, нет прав на запись) —
ничего не падает и битой ссылки в разметке не появится: тег просто ссылается на исходный,
некэшированный файл, как при `minify: false`. При `combine: true` то же самое на уровне бандла —
если объединённый файл записать не удалось, каждый ресурс рендерится отдельным тегом вместо одного
битого.

#### Кэш минификации в APCu (опционально)

Чтение файла и его минификация происходят заново на каждом запросе — статические свойства
(`Manager::$discovered` и т.п.) живут только в рамках одного запроса и обнуляются, как только
процесс PHP-FPM берётся за следующий. Если на сервере включено расширение **APCu**
(`function_exists('apcu_fetch')`), `readContent()` при `minify: true` дополнительно кладёт
результат минификации в APCu — ключ строится из абсолютного пути файла и его `mtime`, так что
изменение файла само по себе даёт новый ключ (инвалидация по факту, а не по TTL). Следующий
запрос, даже в другом воркере, при попадании в кэш пропускает и чтение файла, и сам вызов
`minify()`.

Если APCu не установлен, эта ветка просто не выполняется — поведение полностью совпадает с тем, как
если бы её не было. Ничего не нужно включать отдельно и нечего специально настраивать.

APCu — это один сегмент общей памяти фиксированного размера (`apc.shm_size`) на весь сервер, общий
для всего, что вообще кладёт туда данные (не только `Asset`). Большой файл в нём — плохая идея: он
непропорционально съедает этот бюджет, фрагментирует сегмент и может вытеснить чужие записи.
Поэтому результат минификации крупнее `AssetHandler::APCU_MAX_BYTES` (1024 КБ) в APCu не
складывается — файл всё равно читается и минифицируется корректно, просто без кэширования
результата между запросами.

#### Очистка устаревших файлов кэша и лимит на размер

Раз старые (уже никем не используемые) файлы под прежними хэшами сами по себе не удаляются, для
этого есть `Asset::clean(int $maxAge = 604800, ?int $maxBytes = null)`:

```php
Asset::clean();                      // всё старше 7 дней
Asset::clean(86400);                 // всё старше суток
Asset::clean(604800, 100*1024*1024); // + не больше 100 МБ суммарно в cache/assets
```

По имени файла нельзя узнать, используется ли он прямо сейчас — это зависит от того, что именно
сегодня заэнкьюено в коде, а не от содержимого диска, поэтому очистка не «умная» (не проверяет
ссылки), а по возрасту: файл, который не перезаписывался (т.е. не запрашивался с тем же
содержимым) дольше `$maxAge`, считается более неиспользуемым. Отсюда следствие: `$maxAge` должен
быть заметно больше, чем интервал между деплоями/изменениями файлов, иначе можно удалить то, что
всё ещё используется, но давно не менялось.

Если передан `$maxBytes` — после удаления устаревшего по возрасту метод дополнительно проверяет
суммарный размер того, что осталось в `cache/assets`, и, если он больше лимита, удаляет оставшиеся
файлы от **самого старого к самому новому** (по `mtime`), пока не уложится в бюджет. Это тоже не
«умное» решение по востребованности — просто «старое в первую очередь», как обычный LRU по времени
модификации.

Тот же самый вызов доступен из консоли:

```bash
php artisan asset:clean --max-age=604800 --max-size=104857600
```

Удобно повесить на cron/деплой-скрипт (эта команда — не более чем тонкая обёртка над
`Asset::clean()`, никакой отдельной логики).

> CSS реально минифицируется (`Link::minify()` — рабочий алгоритм). JS-минификация —
> заглушка (`Script::minify()` возвращает код без изменений): безопасная минификация JS требует
> настоящей токенизации, а не регулярок — `//` или `/*` с равным успехом может оказаться внутри
> строки или regex-литерала, и наивная замена рискует сломать код. Если нужна настоящая
> JS-минификация, зарегистрируйте свой провайдер (см. [Регистрация собственных провайдеров](#регистрация-собственных-провайдеров))
> на базе реального минификатора/токенизатора.

### Объединение файлов

`combine: true` — соседние по порядку ресурсы одного провайдера (`css`/`js`/...) и одного
расположения (`toFooter`) объединяются в один файл вместо тега на каждый:

```php
Asset::render(['toFooter' => false], combine: true); // один <link> в <head> вместо N
Asset::render(['toFooter' => true], combine: true);  // один <script> перед </body> вместо N
```

«Соседние» — это соседние в уже отсортированном по зависимостям порядке, поэтому если фильтровать
по расположению, как в примерах выше (раздельно для `head` и для подвала), в один файл попадает
именно то, что и должно было оказаться рядом.

Объединяются только ресурсы с локальным файлом (`path`) — внешний URL (например, скрипт с CDN)
всегда рендерится отдельным тегом, как обычно, и просто прерывает текущую цепочку вместо того чтобы
попасть в неё. Если после разрыва остался только один ресурс подряд — он тоже рендерится как
обычный отдельный тег, без файла-бандла: объединение имеет смысл только от двух файлов подряд.

По той же причине не объединяется ресурс с любым атрибутом, отличным от значения по умолчанию
(`async`, `crossorigin`, `integrity`, свой `class` и т.п.) — при объединении бандл собирается как
новый ресурс только из `uid`/файла/`toFooter`, и такой атрибут был бы потерян молча. Такой ресурс
прерывает цепочку и рендерится сам по себе, ничего не теряя.

Исключение — `data` (инлайн-дамп переменной для JS, `<script>var uid = {...}</script>` перед
основным тегом): такой ресурс **можно** объединять с другими, дамп при этом не теряется, а
рендерится отдельно перед тегом бандла — по одному на каждый объединённый ресурс, у которого
`data` не пуст:

```php
Asset::script('youla', '/assets/js/youla.js', ['data' => ['apiurl' => '/api/']]);
Asset::script('youla-ajax', '/assets/js/youla-ajax.js');
Asset::script('youla-tooltip', '/assets/js/youla-tooltip.js');

Asset::render(['toFooter' => true], combine: true);
// <script>var youla = {"apiurl":"\/api\/"}</script>
// <script id="bundle-js" src=".../cache/assets/js/bundle-<hash>.js"></script>  (все три вместе)
```

Сам `data`-дамп в закэшированный файл бандла не попадает и на его хэш не влияет — это специально:
`data` часто зависит от конкретного запроса/пользователя (например, список API-ключей из БД), и
если зашить его прямо в файл, у бандла на каждый запрос будет новый хэш — кэш перестанет
переиспользоваться, а `cache/assets` начнёт расти файлами-почти-дублями.

```php
Asset::script('vendor', '/assets/js/vendor.js');
Asset::script('main', '/assets/js/main.js');
Asset::script('cdn', '//cdn.example.com/lib.js');   // разрывает цепочку
Asset::script('extra', '/assets/js/extra.js');      // после разрыва — один файл, без пары

Asset::render(['toFooter' => true], combine: true);
// <script id="bundle-js" src=".../cache/assets/js/bundle-<hash>.js"></script>  (vendor+main вместе)
// <script src="//cdn.example.com/lib.js"></script>                            (внешний, отдельно)
// <script src="/assets/js/extra.js"></script>                                  (один, без пары — как обычно)
```

`combine`, `minify` и `inline` полностью независимы — любая комбинация всех трёх допустима:

- `combine: true` (без `minify`/`inline`) — файлы просто склеиваются как есть, без минификации, и
  сохраняются в один файл-бандл; полезно, если хочется меньше запросов, но не хочется терять
  читаемость исходников при отладке.
- `combine: true, minify: true` — то же самое, но каждый файл предварительно проходит через свой
  `minify()`, прежде чем попасть в бандл.
- `combine: true, inline: true` — все файлы в цепочке склеиваются и выводятся одним `<style>`/
  `<script>` прямо в разметке; файл на диск при этом **не пишется вообще** — бандлу, в отличие от
  обычного `combine: true`, не нужен файл, чтобы на него сослаться, раз он и так весь оказывается
  в HTML.
- `combine: true, minify: true, inline: true` — то же самое, но каждый файл сначала
  минифицируется, и уже минифицированные куски склеиваются во встроенный тег.

```php
Asset::render(['toFooter' => true], combine: true, inline: true);
// <script>console.log('vendor');\nconsole.log('main');</script>       (vendor+main вместе, инлайн)
// <script src="//cdn.example.com/lib.js"></script>                    (внешний, отдельно)
// <script src="/assets/js/extra.js"></script>                          (один, без пары — как обычно)
```
